https://github.com/corepool/vibebuddy

将 MicroDuck 的软件分叉并抽象为 **VibeBuddy OS**，这是一个非常关键的架构决策。这不仅是代码的复制，更是将一套为特定硬件（“鸭子”）编写的固件，**提升为一个独立、可扩展、面向多形态机器人的软件平台**。

参考 MicroDuck 的软件架构，VibeBuddy OS 的核心任务是继承其优秀的“服务化”设计理念，并将其发展成一个属于你自己的、更通用的机器人操作系统。

### 🦴 第一步：解剖 MicroDuck —— 它优秀的“微内核”架构

MicroDuck 的软件设计非常精妙，它没有依赖ROS等大型框架，而是采用了一种 **“微内核”式的服务化架构**。其“大脑”由一组用 Rust 编写的独立守护进程（Daemons）组成：

- **`robotd` (控制中枢)**：系统的绝对核心，以 **50Hz** 的频率运行控制循环。它负责执行强化学习策略、驱动所有舵机，并内置**安全层**。所有其他组件的指令都只是“动作意图”，必须经过 `robotd` 的安全校验才能执行。

- **`updaterd` (更新管家)**：负责OTA升级，具备**签名验证**和**失败自动回滚**机制，确保设备不会“变砖”。

- **`configd` (配置中心)**：管理设备的Wi-Fi、身份等配置信息。

- **`btd` (蓝牙服务)**：处理蓝牙通信。

- **`padd` (手柄服务)**：支持游戏手柄控制。

- **`mediad` (媒体服务)**：管理摄像头、音频和WebRTC流。

- **`tofd` (传感器服务)**：读取ToF深度传感器的数据。

这些服务之间通过 **Unix Socket + JSON-RPC 2.0** 进行通信，结构清晰，模块间耦合度极低。这种设计正是 VibeBuddy OS 能够进化成一个通用平台的绝佳起点。

### 🚀 第二步：分叉与进化 —— 从“鸭脑”到“VibeBuddy OS”

将 MicroDuck 的软件分叉，不仅仅是复制代码，而是一个系统的重构和品牌化过程。

#### 1. 分叉策略：如何操作

- **创建分叉 (Fork)**：在 GitHub 上官方仓库页面点击 “Fork” 按钮，创建属于你自己的副本。

- **独立开发**：将你的 Fork 仓库克隆到本地，所有的修改、重构都将在这个独立的仓库中进行。

- **定期同步**：你可以将官方 MicroDuck 仓库添加为上游（upstream）远程仓库，定期合并官方的更新和修复。

#### 2. 架构演进：从“鸭子专用”到“通用平台”

这是最重要的一步。你需要对代码进行重构，将“MicroDuck 硬件”的特定逻辑剥离出来。

| 组件 | MicroDuck (分叉前) | VibeBuddy OS (分叉后) | 关键动作 |
| - | - | - | - |
| **硬件抽象层 (HAL)** | 与特定舵机型号、IMU 型号强耦合。 | **定义标准硬件接口**，如 `Motor`, `Imu`, `Camera`。 | 抽象出硬件接口，使 OS 不依赖具体硬件。 |
| **核心服务 (`robotd`等)** | 服务名称和功能绑定“鸭子”概念。 | **重命名并泛化**，如 `control\_daemon`, `update\_daemon`。 | 修改代码，移除与“鸭子”相关的硬编码，使其逻辑通用。 |
| **配置文件** | 舵机ID、IMU方向等参数写死在代码或特定配置中。 | **引入“硬件描述文件” (Hardware Descriptor)**。 | 为每款机器人（Chicken, Cat, Doge）创建一个独立的配置文件。 |
| **构建系统** | 构建目标为 `microduck` 固件。 | **支持多目标构建**，如 `make vibe-chicken`, `make vibe-cat`。 | 修改构建脚本，根据目标加载不同的硬件描述文件和相关驱动。 |


通过这套架构，VibeBuddy OS 就变成了一个通用的“机器人大脑”。当开发新产品（如 Vibe Cat）时，你只需提供新的“硬件描述文件”和对应的外设驱动，核心的 OS 代码无需大改，这便是形成了“技术优势”的基础。

### 🎨 第三步：品牌塑造 —— 打造“VibeBuddy OS”的独立身份

技术分叉完成后，必须进行品牌区分。

  - 全面替换 README、文档、代码注释中的 `Microduck`、`duck` 等字样。

  - 将 `duckctl` 等命令行工具重命名为 `vibectl` 或 `buddyctl`。

  - 将默认的“鸭叫”声音，替换为具有 Vibe 家族特色的启动音效。

- **视觉与社区层面**：

  - 设计全新的 Logo、启动界面和文档风格。

  - 建立独立的社区（Discord/Slack）和官网，明确 VibeBuddy OS 的定位和愿景。

  - 在宣传中始终强调 **“VibeBuddy OS 是一个通用的机器人操作系统，它驱动着 Vibe Chicken, Cat, Doge 等整个产品线”**。

### 🗺️ 第四步：规划开发路线图

将分叉和抽象工作转化为可执行的任务：

1. **第一阶段：代码分叉与品牌替换 (1-2周)**

将 MicroDuck 的软件分叉为 VibeBuddy OS，核心就是\*\*“继承精髓，重构躯体，塑造灵魂”\*\*。

### 3. 功能需求

#### 3.1 核心服务模块

VBOS v1.0 包含 **7 个核心守护进程**：

| 服务 | 功能描述 | 优先级 |
| - | - | - |
| **robotd** | 50Hz 实时控制循环、RL 策略执行、安全控制、舵机/IMU 驱动 | P0 |
| **updaterd** | OTA 升级、签名验证、失败自动回滚、版本管理 | P0 |
| **configd** | Wi-Fi 配置、设备身份管理、网络状态 | P0 |
| **btd** | 蓝牙 LE 通信、手机配对与控制 | P1 |
| **padd** | 游戏手柄支持（USB/BLE） | P1 |
| **mediad** | 摄像头视频流、音频采集、WebRTC 推流 | P1 |
| **tofd** | 8×8 ToF 深度传感器数据读取与发布 | P2 |


**需求详述**：

##### 3.1.1 robotd — 控制守护进程

- **REQ-CORE-001**：以 **50 Hz 固定频率**运行控制循环

- **REQ-CORE-002**：在单个事务中读取总线上所有设备（15 舵机 + 1 IMU）

- **REQ-CORE-003**：计算 15 个关节目标值并批量写回

- **REQ-CORE-004**：内置**安全层**，校验所有动作意图的可行性

- **REQ-CORE-005**：支持**策略热切换**，运行时更换 RL 策略文件

- **REQ-CORE-006**：提供 `robot.init` 和 `robot.relax` IPC 方法作为紧急逃生口

- **REQ-CORE-007**：支持**多硬件形态**，通过硬件描述文件适配不同机型

##### 3.1.2 updaterd — 更新守护进程

- **REQ-UPD-001**：从 GitHub Release / Hugging Face Hub 下载更新包

- **REQ-UPD-002**：验证更新包的数字签名

- **REQ-UPD-003**：执行版本切换，重启相关服务

- **REQ-UPD-004**：**健康检查**：新版本启动后验证 robot.health

- **REQ-UPD-005**：**自动回滚**：健康检查失败则自动切回旧版本

- **REQ-UPD-006**：`configd`、`updaterd`、`btd` 不依赖 robotd，确保控制 loop 死掉时仍可更新/回滚

##### 3.1.3 服务间通信

- **REQ-IPC-001**：所有服务通过 **Unix Socket** 通信

- **REQ-IPC-002**：使用 **JSON-RPC 2.0** 协议，NDJSON 格式（每行一个 JSON 对象）

- **REQ-IPC-003**：每个服务拥有独立的 socket（如 `/run/robotd/robot.sock`）

- **REQ-IPC-004**：`mediad` 和 `robotd` 可读取 `tofd` 发布的深度数据

##### 3.1.4 硬件抽象层（HAL）

- **REQ-HAL-001**：定义标准硬件接口：`Motor`、`Imu`、`Camera`、`ToF`

- **REQ-HAL-002**：每种机型提供独立的**硬件描述文件**（YAML/TOML 格式）

- **REQ-HAL-003**：硬件描述文件包含：舵机 ID 映射、IMU 方向、关节限位、默认 PID 参数

- **REQ-HAL-004**：OS 启动时根据硬件描述文件加载对应驱动和参数

#### 3.2 仿真与训练

- **REQ-SIM-001**：提供基于 **MuJoCo** 的仿真环境

- **REQ-SIM-002**：仿真环境精确模拟电机摩擦、电池电压变化、控制延迟、舵机齿隙

- **REQ-SIM-003**：支持 **PPO** 算法训练

- **REQ-SIM-004**：支持**领域随机化**（Domain Randomization）缩小 Sim2Real 差距

- **REQ-SIM-005**：训练完成的策略导出为 **ONNX** 格式部署到真机

- **REQ-SIM-006**：提供**统一的 61 维观测接口**，使多套策略可热切换

#### 3.3 用户交互

- **REQ-UI-001**：手机 App 通过 **BLE** 控制机器人（行走、姿态、行为触发）

- **REQ-UI-002**：手机 App 通过 **WebRTC** 查看实时摄像头画面

- **REQ-UI-003**：支持**游戏手柄**控制（USB 有线 / BLE 无线）

- **REQ-UI-004**：提供命令行工具 `vibectl` 进行本地调试和控制

**架构核心原则**：

1. **`robotd` 是唯一触碰硬件的服务**——其他所有服务只能发送“动作意图”

2. **三个服务（configd、updaterd、btd）不依赖 robotd**——确保控制崩溃时仍可恢复

3. **`tofd` 是只读发布者**——mediad 和 robotd 读取其数据，但它不读取任何人的数据

│  • UNINIT → RELAXED: robot.init() 成功，舵机上电                          │

### 3. 构建与测试

#### 3.1 构建要求

| Cross | 最新 | 交叉编译工具 |
| Systemd | 249+ | 服务管理（目标平台） |


#### 3.2 构建命令

```
\# 开发环境构建（本地）  
cargo build --workspace  
  
\# 发布构建（优化）  
cargo build --release --workspace  
  
\# 交叉编译到 ARM 目标  
cross build --release --target aarch64-unknown-linux-gnu  
  
\# 构建特定守护进程  
cargo build -p robotd  
  
\# 运行所有测试  
cargo test --workspace  
  
\# 运行特定测试

```

### 4. 编码规范

#### 4.1 Rust 编码规范

- 遵循 **Rust API Guidelines** ([https://rust-lang.github.io/api-guidelines/](https://rust-lang.github.io/api-guidelines/))

- 使用 `rustfmt` 自动格式化

- 使用 `clippy` 进行 lint 检查

- 所有 `unsafe` 代码必须有详细的安全注释

```
\# 格式化  
cargo fmt --all  
  
\# Lint 检查  
cargo clippy --workspace -- -D warnings
```

#### 4.2 命名规范

| 类型 | 规范 | 示例 |
| - | - | - |
| 类型 (struct/enum) | PascalCase | `ControlLoop`, `SafetyGuard` |
| 函数/方法 | snake\_case | `run\_loop()`, `check\_safety()` |
| 变量 | snake\_case | `joint\_targets`, `imu\_data` |
| 常量 | SCREAMING\_SNAKE\_CASE | `MAX\_JOINT\_LIMIT` |
| 模块 | snake\_case | `control`, `safety` |
| Trait | PascalCase | `Motor`, `Imu` |


#### 4.3 错误处理

- 使用 `anyhow` 和 `thiserror` 进行错误处理

- 所有公共 API 返回 `Result\<T, Error\>`

- 错误类型应实现 `std::error::Error`

```
// 示例  
\#\[derive(Debug, thiserror::Error)\]  
pub enum RobotdError \{  
    \#\[error("Bus error: \{0\}")\]  
    Bus(\#\[from\] BusError),  
    \#\[error("Safety violation: \{0\}")\]  
    Safety(String),  
    \#\[error("Policy load failed: \{0\}")\]  
    Policy(String),  
\}
```

### 5. IPC 协议规范

#### 5.1 消息格式

所有 IPC 消息使用 **JSON-RPC 2.0** 格式：

```
// 请求  
\{"jsonrpc":"2.0","method":"robot.cmd","params":\{"target":"walk"\},"id":1\}  
  
// 响应  
\{"jsonrpc":"2.0","result":\{"status":"ok"\},"id":1\}  
  
// 错误响应  
\{"jsonrpc":"2.0","error":\{"code":-32000,"message":"Safety violation"\},"id":1\}  
  
// 通知 (无 id)  
\{"jsonrpc":"2.0","method":"robot.health","params":\{"status":"running"\}\}
```

#### 5.2 核心 RPC 方法

| 服务 | 方法 | 描述 |
| - | - | - |
| robotd | `robot.health` | 查询健康状态 |
| robotd | `robot.cmd` | 发送动作指令 |
| robotd | `robot.init` | 初始化舵机 |
| robotd | `robot.relax` | 释放舵机 |
| robotd | `robot.policy.load` | 加载策略文件 |
| robotd | `robot.policy.switch` | 切换策略 |
| updaterd | `update.check` | 检查更新 |
| updaterd | `update.apply` | 应用更新 |
| configd | `net.wifi.set` | 设置 Wi-Fi |
| configd | `system.name.set` | 设置设备名称 |
| btd | `bt.pair` | BLE 配对 |
| padd | `pad.bind` | 手柄绑定 |
| mediad | `media.stream.start` | 启动视频流 |
